# Check release wiring

This skill verifies that the set of OpenStack releases under `releases/`
and the rest of the repo **stay in lockstep**: every release directory is
fully wired into CI, tests, and deploy defaults, and no reference points
at a release that no longer (or does not yet) exist.

It is repeatable — run it any time, especially after adding a new
`releases/<version>/` directory, after removing an old one, or before
tagging a release.

## What release wiring means here

The build/test matrices auto-discover releases (`hack/ci-generate-build-matrix.sh`
scans `releases/*/`, services come from `source-refs.yaml` keys, the e2e
legs load `<svc>:<release>` for every release `hack/ci-service-image-releases.sh`
prints, and the Renovate globs cover `releases/**`) — but several touch
points are enumerated by hand and drift silently. The repo carries eight
services (`source-refs.yaml` keys), six Tempest legs, and seven
`release-upgrade` suites; every table row below applies per service.

| Layer | Where it lives | Source of truth |
|---|---|---|
| Release config files | `releases/<version>/{source-refs,test-refs,extra-packages}.yaml`, `upper-constraints.txt`, `test-excludes/<svc>.txt` | `tests/container-images/verify_release_config.sh` |
| Option catalogs | `operators/<op>/api/v1alpha1/catalogs/<version>.json` for every operator with a `catalogs/` dir (seven today), generated by `hack/gen-option-catalog.sh <op> <version>` | Test 8 of the verifier (keystone, glance); build-images.yaml "Verify option catalog" (`--check`: keystone, glance, neutron, cinder, nova); without one the webhook skips `extraConfig` validation for that release |
| Overrides and patches | `overrides/<version>/constraints.txt` (`-horizon` strip, `lhafile===` pin), `patches/<svc>/<version>/*.patch` | `scripts/apply-constraint-overrides.sh`, `hack/ci-build-service-image.sh` — a missing patch dir builds the service unpatched, silently |
| Tempest config | `tests/tempest/<svc>-<slug>/` for every service in `ALL_TEMPEST_SERVICES` (keystone, glance, barbican, neutron, cinder, nova), slug = version with `.` → `-`: `exclude-tests.txt`, `include-tests.txt`, `tempest.conf`, plus 1–16 numbered CR fixtures | `hack/ci-generate-tempest-matrix.sh` — **hard-fails the pipeline** when any directory is missing, and emits the CR names the CI job waits on |
| Per-release e2e variant | `tests/e2e/<svc>/basic-deployment` (pins the default release) plus `basic-deployment-<slug>/` for every other release, for each of the eight services | hand-maintained fixtures with hard-coded names and image refs; [[check-service-parity]] P6 checks the latest-release variant exists |
| E2E fixture release pins | every `tag:`, `openStackRelease:`, `installedRelease:`, and `ghcr.io/c5c3/<img>:<YYYY.N>` in `tests/e2e*/` (~1,000 today, the tempest client image included) | the `releases/` directory set |
| Placed-services release pins | `tests/e2e-multicluster/placed-services/*.yaml` (`repository:` + `tag:`) and the ci.yaml `e2e-multicluster` job's image preloads | hand-maintained; the suite runs one release, not a matrix |
| Default-release references | `deploy/kind/controlplane/controlplane.yaml` `openStackRelease`, `hack/deploy-infra.sh` `cp_release`, every `${VAR:-YYYY.N}` fallback in `hack/*.sh` (three `RELEASE:-`, `IMAGE_TAG:-` in `perf-reconcile-benchmark.sh`), image tags in `.github/workflows/ci.yaml` | the `releases/` directory set |
| Renovate | `tests/unit/renovate/*_test.sh` probes and the per-release `packageRules` in `renovate.json` (the `neutron-tempest-plugin` holds) | the `releases/` directory set |
| Upgrade-path e2e | `tests/e2e/<svc>/release-upgrade/` (barbican, cinder, glance, keystone, neutron, nova, placement), `tests/e2e/keystone/upgrade-flow/`, `upgrade-flow/02-patch-skip-level.yaml`, `tests/e2e/keystone/upgrade-abort/` | `release.IsSequentialUpgrade` and the sorted release list |
| Version pattern | the `+kubebuilder:validation:Pattern` on every `OpenStackRelease` field (ControlPlane and seven service CRDs), `controlPlaneReleaseRegexp`, the `release.ParseRelease` minor guard, 16 generated CRD YAMLs | the three-layer agreement documented at `operators/c5c3/api/v1alpha1/controlplane_types.go` |

The authoritative gates are `tests/container-images/verify_release_config.sh`,
the shell unit tests under `tests/unit/` (`make test-shell`, including
`tests/unit/ci/{neutron,cinder,nova}_e2e_matrix_test.sh`, which hold the
generator's CR names against the Tempest fixtures), and the CI matrix
generators themselves. This skill defers to those for file-format
correctness and adds the cross-cutting check they cannot express: "is
every release fully wired, and does every release-shaped reference
resolve?"

A wiring finding is any release directory missing a hand-enumerated touch
point, or any reference to a version that has no `releases/<version>/`
directory.

## Procedure

Work through these steps in order and report findings at the end.

### 1. Run the deterministic audit

```bash
bash .claude/skills/check-release-wiring/scripts/audit-release-wiring.sh
```

The script catches the mechanically-checkable gaps and prints an
inventory. Exit code `1` means at least one `[FAIL]`. Pass `--full` to
chain `verify_release_config.sh` and the CI matrix generators after the
inventory. Interpret:

- **L1** — every `releases/<version>/` carries the four mandatory files
  and every `test-excludes/*.txt` maps back to a `source-refs.yaml` key
  (Test 7). Every operator with a `catalogs/` directory carries
  `<version>.json`, and no catalog outlives its release. A service pinned
  in `upper-constraints.txt` (horizon) must be stripped by a `-<svc>` line
  in `overrides/<version>/constraints.txt`. `overrides/<v>/` and
  `patches/<svc>/<v>/` for a removed release are orphans; a release a
  sibling patches but this one does not is `[INFO]` (confirm the fix
  landed upstream). Differing service or `test-refs.yaml` key sets across
  releases are `[INFO]`.
- **L2** — `ALL_TEMPEST_SERVICES` is parsed from the generator (a parse
  failure is a `[FAIL]`, never a keystone-only fallback). Per release ×
  service: the directory, the three text files, and at least one `*.yaml`
  exist; every release pin in the directory (tags, `openStackRelease`,
  `ghcr.io/c5c3/*` refs including the tempest client image) names the
  directory's release; every dashed or underscored slug on a
  non-comment line (CR, Service, hostname, database names) is the
  directory's own. With `jq`, the generator is run (output to stdout,
  nothing written) and every `cr-name` / `<svc>-cr-name` it emits must be
  some fixture's `metadata.name`. Any `tests/tempest/<svc>-<slug>/` whose
  release is gone or whose service the generator lacks is an orphan.
- **L3** — every service with `tests/e2e/<svc>/basic-deployment/` covers
  every release: the plain suite's own `NN-<svc>-cr.yaml` pins the
  default release (the kind ControlPlane `openStackRelease`; a mismatch
  is a half-done default move), and `basic-deployment-<slug>/` covers
  each other release. Variants must pin their own release in every field
  and service image ref, carry only their own slug in names, and not
  outlive their release. The tempest client image is exempt: the e2e legs
  load one tempest tag (`ghcr.io/c5c3/tempest:2025.2` today) and every
  e2e fixture's Jobs run it, whatever release the suite deploys. Then a sweep over every `tests/e2e*/` fixture: each
  release a pin names must exist (the skip-level and stuck-upgrade
  fixtures are excluded; L6 checks them). Last, each placed-services
  `repository:` + `tag:` pair must appear as `/<img>:<tag>` in the ci.yaml
  `e2e-multicluster` job, and each release-tagged preload there must
  match the fixture pin.
- **L4** — every default-release reference resolves to an existing
  release: the kind quick-start ControlPlane, the deploy-infra image
  preload, every `${VAR:-YYYY.N}` fallback in `hack/*.sh`, and every
  `:<YYYY.N>` image tag hard-coded in `ci.yaml`.
- **L5** — the Renovate regression tests and the `releases/<v>/` paths in
  `renovate.json` `matchFileNames` name only existing releases. A retired
  probe breaks `make test-shell`; a retired rule is dead config.
- **L6** — every `release-upgrade` and `upgrade-flow` suite tests the
  newest sequential transition: `from` is the `tag:` of the service's own
  `NN-<svc>-cr.yaml` (nova: `04-nova-cr.yaml`, neutron: `02-neutron-cr.yaml`),
  `to` the `tag:` of `NN-patch-upgrade.yaml`; `openStackRelease` agrees
  with the tag in both, and helper CRs and assertions name only `from` or
  `to`. The skip-level target must be neither wired nor the sequential
  successor of `to`. `upgrade-abort` must start at a wired release and
  wedge on its sequential successor. Its stuck patch pulls from a
  registry under the reserved `.invalid` TLD, so the wedge holds whatever
  releases exist, and its abort patch must restore the start repository
  and tag. A stuck patch on the real repository (the old shape) wedges
  only while the target is **not** wired — the e2e leg loads every wired
  release's image — and is checked that way.
- **L7** — the ControlPlane marker equals `controlPlaneReleaseRegexp`,
  every other `OpenStackRelease` marker under `operators/*/api/` equals
  it, every generated CRD with an `openStackRelease` property carries the
  pattern, and `release.ParseRelease` still enforces the `{1,2}` minor
  set the `[12]` class encodes.

### 2. Cross-reference the inventory

The script checks shapes, not semantics. Using the printed inventory,
confirm by hand:

1. For each release, that the `source-refs.yaml` component versions are
   the intended upstream tags for that OpenStack series, and that
   `test-refs.yaml` pins tempest and every plugin (keystone, barbican,
   neutron, cinder) at versions the release's `upper-constraints.txt`
   can install — the `renovate.json` holds record the known conflicts.
2. That `upper-constraints.txt` was snapshotted from the matching
   upstream `stable/<series>` branch, and that every
   `overrides/<version>/constraints.txt` entry and every
   `patches/<svc>/<version>/` patch is still needed.
3. That `ci.yaml`'s hard-coded `<svc>:<version>` tags (the image-upgrade
   re-tag in e2e-operator, the kind preloads of e2e-chaos,
   e2e-controlplane, e2e-controlplane-sso, e2e-external-keystone,
   e2e-prometheus, e2e-operator-upgrade, e2e-multicluster) still name
   the release the fixtures actually use — the script verifies
   existence, not intent (L3 pairs only the e2e-multicluster side).
4. That the Tempest per-release `exclude-tests.txt` entries were
   re-triaged (`re-evaluate-on:` comments name the plugin version).
5. Docs that enumerate releases: `docs/reference/testing/tempest-test-infrastructure.md`
   lists every `tests/tempest/<svc>-<slug>/` and the generator's
   per-entry table; `docs/guides/glance/filter-web-download-imports.md`
   code-imports `tests/tempest/glance-2025-2/02-glance-cr.yaml`. When
   the default moves, sweep `docs/` examples for the old tag
   ([[check-doc-drift]] covers the load-bearing pages).

### 3. Run the authoritative gates

```bash
bash tests/container-images/verify_release_config.sh
make test-shell
GITHUB_OUTPUT=/dev/null GITHUB_EVENT_NAME=pull_request bash hack/ci-generate-build-matrix.sh
GITHUB_OUTPUT=/dev/null bash hack/ci-generate-tempest-matrix.sh
```

Trust these over the L1–L7 smoke checks when they disagree.

### 4. Report

Produce a concise summary grouped by severity:

- **HIGH** — a release missing any service's Tempest config directory
  (pipeline-wide CI failure); a default-release reference, fixture pin,
  or renovate probe naming a non-existent release; a missing option
  catalog the verifier or build-images checks; a version-pattern
  divergence between markers, webhook, or generated CRDs.
- **MEDIUM** — a release without basic-deployment coverage for a
  service; an upgrade-path suite not covering the newest transition; an
  `upgrade-abort` that no longer wedges (target wired on the real
  repository, or an abort patch that keeps the unresolvable registry); a Tempest dir or variant
  pinning the wrong tag, image ref, or slug; a generator CR name no
  fixture defines; an orphan Tempest dir, variant, catalog, overrides, or
  patch directory; a dead per-release `renovate.json` rule.
- **LOW** — a release a sibling patches but this one does not; service or
  `test-refs.yaml` key sets differing across releases without a recorded
  reason; stale release examples in prose.

For each finding give one line with a `file:line` reference for both
the release side and the referencing side. End with a wired / not-wired
verdict per release.

## Drift patterns

These recurring shapes are worth grepping for first:

1. **New release, keystone-only Tempest clone.** `releases/2026.2/` lands
   with `tests/tempest/keystone-2026-2/` but not the glance, barbican,
   neutron, cinder, and nova directories — the matrix generator
   hard-fails and blocks every CI run, not just Tempest.
2. **Multi-CR Tempest dir cloned without renaming.** The directory is
   copied but one fixture keeps `-2026-1` in a CR name, a `_2026_1`
   database, or `ghcr.io/c5c3/nova:2026.1` in the fake compute — the leg
   times out waiting on a CR the generator names but no fixture creates,
   or silently tests the wrong release.
3. **Variant fixture cloned without retagging.** A
   `basic-deployment-<slug>/` variant copied from the previous one keeps
   the old `tag:` or the old `ghcr.io/c5c3/<svc>:<tag>` ref — the suite
   silently tests the wrong release.
4. **New release wedges nothing.** A stuck-upgrade suite that relies on
   its target having no image breaks the day that release is added: the
   image is loaded, the upgrade completes, and the abort suite fails.
   `upgrade-abort` avoids it by pulling the target from `registry.invalid`.
5. **Upgrade suites stuck on the previous transition.** A new release is
   added but some of the eight upgrade suites still test the old pair.
6. **Removed release, orphan references.** `releases/2025.2/` is deleted
   but ~900 fixture pins, the plain basic-deployment suites, the kind
   ControlPlane default, the `RELEASE:-2025.2` fallbacks, the option
   catalogs, `overrides/2025.2/`, `patches/*/2025.2/`, the renovate
   probes and hold rule, and the docs code-import still name it.
7. **Pattern widened in one layer only.** A future `YYYY.3` cadence
   change edits `release.ParseRelease` but not the eight CRD markers (or
   vice versa) — the API server and the webhook disagree about which
   versions are valid.

## Notes

- This skill is read-only; the deterministic script edits nothing (the
  L2 generator run writes its output to stdout). Apply fixes as a
  separate, explicitly-scoped task — [[prepare-new-release]] is the
  guided path for adding a release.
- The L2 service list tracks `ALL_TEMPEST_SERVICES`; the L3 service list
  is every `tests/e2e/<svc>/basic-deployment/` directory; L6 covers every
  `release-upgrade/`, `upgrade-flow/`, and `upgrade-abort/` directory.
  A new service or suite is picked up without editing the script, as
  long as it keeps the `NN-<svc>-cr.yaml` / `NN-patch-upgrade.yaml` file
  naming.
- Pair this with [[check-renovate-coverage]] — that skill checks the
  release pins are *trackable* by Renovate; this skill checks the
  release directories are *wired*. With [[check-service-parity]] for the
  latest-release variant of a newly onboarded service, and with
  [[check-doc-drift]] for the prose that references release versions.
