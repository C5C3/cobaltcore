# RFC: CobaltCore Release Management

## 1. Summary

This RFC proposes a standardized release management process for CobaltCore, built around two release channels: **Release Candidate (RC)** and **Stable**.

The approach is to continue developing on `main`, create a dedicated release branch when preparing a release, and publish release candidates from that branch for validation in real environments.

Once a release candidate has been fully validated, that exact build is promoted to stable without rebuilding the underlying artifacts.

Each release should also provide a coordinated collection of installation artifacts, release notes, compatibility information, and software supply chain metadata.

The goal is to make releases predictable, reproducible, traceable, and straightforward for users to consume.

## 2. Motivation

CobaltCore already has substantial CI/CD infrastructure capable of building and publishing container images and Helm charts, generating SBOMs for service images, and creating GitHub Releases.

However, we do not yet have an agreed process for deciding what gets released, how release candidates are validated, how fixes are incorporated during stabilization, or how users consume a coordinated release.

A standardized release process should address the following:

- Establish a clear distinction between development builds, release candidates, and stable releases.
- Allow release candidates to be deployed and validated in real environments.
- Allow ongoing development on `main` without unintentionally introducing new changes into a release being prepared.
- Provide a straightforward mechanism for backporting selected fixes.
- Ensure stable releases contain exactly the artifacts that were previously tested.
- Automatically generate and publish release notes describing what changed.
- Publish a coherent collection of installable artifacts and their immutable references.
- Clearly communicate supported OpenStack releases, platform compatibility, and component dependencies.
- Make SBOMs, provenance, and artifact verification information available to users.

## 3. Proposed Release Channels

We propose two public release channels.

| Channel | Version example | Purpose |
|---|---|---|
| Release Candidate | `0.1.0-rc.1` | Pre-release builds available for testing and validation |
| Stable | `0.1.0` | Validated, recommended release |

Versions follow Semantic Versioning, starting at `0.1.0`.

Git tags use the `v` prefix, for example `v0.1.0-rc.1` and `v0.1.0`.

### 3.1 Release Candidate

An RC represents a specific, immutable snapshot of a release branch that is ready for testing.

Each published candidate gets an incrementing identifier:

- `0.1.0-rc.1`
- `0.1.0-rc.2`
- `0.1.0-rc.3`

The sequence increments whenever a new candidate is published. An existing candidate must not be replaced or overwritten.

RCs are published as GitHub pre-releases and include the artifacts required to deploy and validate the release.

### 3.2 Stable

A stable release is an RC that has completed the required validation.

For example, if `0.1.0-rc.3` passes validation, it is promoted to `0.1.0`.

**Promotion must not trigger a rebuild.** The stable release must refer to the same source commit and identical deployable artifacts as the validated RC.

The stable version is the public identifier of the promoted distribution. It does not require changing the version embedded in an already published component artifact.

## 4. Release Branching Strategy

We propose keeping `main` as the primary development branch and creating dedicated release branches when a release is ready for stabilization.

Release branches follow the convention:

`release/<major>.<minor>`

For example:

`release/0.1`

### 4.1 Starting a release

A release begins when the maintainers decide that the current state of `main` is sufficiently complete to begin stabilization.

At that point:

1. Create `release/0.1` from a selected commit on `main`.
2. Establish the intended release scope and version (`0.1.0`).
3. Publish the first RC from the release branch when the release checks pass.
4. Start testing the RC in representative deployment environments.

The release branch becomes the source of truth for that release series.

Meanwhile, development continues on `main` without being blocked by release validation.

### 4.2 Incorporating fixes

After a release branch has been created, we should avoid merging `main` into it directly.

Instead, changes should be selectively incorporated.

The preferred workflow is:

1. A bug is discovered during release validation.
2. A fix is implemented and merged into `main`.
3. The corresponding commit is cherry-picked into a PR targeting `release/0.1`.
4. The backport is reviewed and validated.
5. A new RC is published from the updated release branch.

In exceptional cases, a fix may be implemented directly against the release branch, but it must also be incorporated into `main` to prevent divergence.

Only fixes required for stabilization should normally enter a release branch. New functionality continues to target `main`.

### 4.3 Maintaining release branches

After `0.1.0` becomes stable, `release/0.1` may remain available for maintenance releases.

A subsequent fix can follow the same process:

`0.1.1-rc.1` → `0.1.1`

A new minor release, such as `0.2.0`, starts from a separate `release/0.2` branch cut from `main`.

## 5. Release Lifecycle

The proposed lifecycle is:

### 5.1 Prepare

- Agree on release scope and version.
- Cut the release branch from `main`.
- Resolve release-blocking issues.
- Confirm the intended OpenStack compatibility matrix.

### 5.2 Publish RC

- Run the required CI checks against the release branch.
- Build and publish the complete release artifact set.
- Generate release notes, compatibility information, and a release manifest.
- Produce or collect SBOMs and provenance for the published artifacts.
- Record exact source commits and artifact digests.
- Create a versioned Git tag and GitHub pre-release.

### 5.3 Validate

Deploy the RC into representative environments.

Validation should cover applicable integration and E2E tests, installation and upgrade paths, compatibility with the declared OpenStack releases, and known release-blocking regressions.

The exact artifact versions and digests recorded by the candidate must be the ones used during validation.

### 5.4 Stabilize

If validation identifies issues, merge the required fixes into the release branch and publish a new RC.

Each new candidate restarts validation for the changed artifacts. Previously validated results must not be assumed to apply to a different build.

### 5.5 Promote

Once the candidate passes all required checks:

- Create the stable tag (`v0.1.0`) pointing to the same commit as the validated RC.
- Verify the identity and integrity of the previously published artifacts.
- Promote the release without rebuilding or repackaging its deployable artifacts.
- Publish the stable GitHub Release using the approved release notes, installation instructions, compatibility information, and artifact references.
- Identify the exact RC that was promoted.

The stable release is then available for users to install or upgrade.

## 6. Pull Request and Commit History Policy

We propose adopting **squash merging** for pull requests targeting `main` and release branches.

Each merged PR should result in a single commit representing a logical change.

This provides a mostly linear history, makes individual changes easier to identify and backport, and simplifies comparing release branches.

For backported changes, the PR description or resulting commit message should preserve a reference to the original PR and commit on `main`.

Branch protection should require reviews and relevant CI checks before merging into `main` or `release/*`.

The release process should not require force-pushing or rewriting published release history.

## 7. Release Artifacts and Versioning

A CobaltCore release should represent a **coordinated, reproducible distribution**, rather than an isolated Git tag or collection of independently published component versions.

The release should provide everything a user needs to identify, install, upgrade, or reproduce a specific CobaltCore version.

### 7.1 Required artifacts

We propose publishing the following artifacts with every RC and stable GitHub Release.

| Artifact | Purpose |
|---|---|
| Operator Helm charts (`.tgz`) | Versioned installation packages for CobaltCore operators |
| Installation manifests (`.yaml`) | Rendered Kubernetes resources for direct installation and GitOps |
| Release manifest (`.json` or `.yaml`) | Inventory of component versions, image references, digests, and compatibility |
| Compatibility matrix (`.yaml`) | Supported Kubernetes and OpenStack releases and relevant constraints |
| SBOMs (`.cyclonedx.json`) | Software dependency inventory for the released container images |
| `SHA256SUMS` | Integrity verification for downloadable release files |
| Release notes | Changes, breaking changes, upgrades, known issues, and compatibility |

Container images remain distributed through GHCR. GitHub Releases should reference their immutable digests rather than attach container image archives.

Where installation requires multiple stages, installation bundles should be separated by purpose and document their prerequisites and execution order.

### 7.2 Release manifest

CI should generate a machine-readable release manifest describing the complete distribution.

This manifest acts as the central inventory of the artifacts belonging to a release.

It should include:

- CobaltCore distribution version and candidate identifier.
- Source commit SHA.
- Supported OpenStack release series.
- Component names and versions.
- Container image references and digests.
- Operator Helm chart versions and OCI digests.
- References to installation manifests.
- SBOM and provenance references.

For example, a release manifest could contain:

```yaml
version: 0.1.0-rc.3
sourceCommit: "<git-sha>"

openstack:
  supported:
    - "2026.1"
    - "2026.2"

components:
  - name: keystone-operator
    chart:
      version: "<component-version>"
      digest: "sha256:..."
    image:
      reference: "ghcr.io/c5c3/keystone-operator"
      digest: "sha256:..."

  - name: keystone
    openstackRelease: "2026.1"
    image:
      reference: "ghcr.io/c5c3/keystone"
      digest: "sha256:..."
    sbom: "sbom-keystone-2026.1.cyclonedx.json"
```

*The values above are illustrative, not a verified compatibility declaration.*

The generated manifest must describe the actual artifacts produced and validated by CI.

During stable promotion, the original manifest remains unchanged. Separate promotion metadata may identify the stable version and the RC from which it was promoted.

### 7.3 Project versus component versions

The CobaltCore distribution version is separate from the versions of individual components.

For example, CobaltCore `0.1.0` may contain operator Helm charts with their own version numbers and OpenStack service images built for `2026.1` and `2026.2`.

The existing `releases/<OpenStack-version>/` directories continue to describe supported OpenStack releases, not CobaltCore distribution versions.

This distinction is particularly important for Helm OCI charts: changing a chart's internal version to match the promoted stable version would require repackaging it and would violate artifact immutability.

Instead, the stable distribution points to the already validated chart versions and digests.

The current `v*` pipeline packages charts under the Git tag version. That behavior must be reconciled with this model to avoid version collisions and unintended artifact changes.

Related: [#1589 — Independent release versions for Keystone federation proxy](https://github.com/C5C3/cobaltcore/issues/1589).

## 8. OpenStack Compatibility and Dependencies

CobaltCore supports multiple OpenStack release series, with version-specific source references, dependency constraints, and image builds.

A CobaltCore distribution release must clearly identify which OpenStack series it supports and the precise component artifacts associated with each.

### 8.1 Compatibility matrix

Each GitHub Release should display a concise compatibility table.

For example:

| CobaltCore | OpenStack series | Compatibility |
|---|---|---|
| `0.1.0` | `2026.1` | Subject to release validation |
| `0.1.0` | `2026.2` | Subject to release validation |

The supported OpenStack release list should be derived from the release configuration under `releases/`.

For each series, the release metadata should link back to:

- `releases/<version>/source-refs.yaml`
- `releases/<version>/upper-constraints.txt`
- Relevant dependency overrides and lock files
- The corresponding published service image digests

However, **having a configuration directory or successfully building an image is not sufficient to claim compatibility**.

A series should only be marked supported once the required release validation has passed.

The release should distinguish tested compatibility from any additional experimental or unvalidated configurations.

### 8.2 Component dependency mapping

The release manifest should identify which components are shared across OpenStack versions and which are specific to a particular series.

This is especially important for service images whose tags and dependency sets are derived from their upstream OpenStack releases.

The generated dependency mapping allows users and deployment tooling to select a coherent set of CobaltCore operators and service images without manually reconstructing the relationships between versions.

### 8.3 Upgrade compatibility

Release notes should also communicate:

- Supported Kubernetes versions.
- Known OpenStack compatibility limitations.
- Breaking changes to operator APIs or CRDs.
- Required migration or upgrade steps.
- Whether upgrades from previous CobaltCore versions have been tested.

CI should derive what it can from committed configuration and test results, while maintainers review claims that cannot be established automatically.

## 9. Software Bill of Materials and Supply Chain Security

We propose making SBOMs and provenance part of the public release contract.

An **SBOM (Software Bill of Materials)** identifies the software components and dependencies contained in an artifact. It helps users assess vulnerabilities, audit dependencies, and understand what they are deploying.

### 9.1 Reuse existing infrastructure

CobaltCore already generates CycloneDX SBOMs for service container images through the `supply-chain-attest` GitHub Action.

The existing workflow also performs vulnerability scanning with Grype, generates signed SBOM and build provenance attestations, and signs images using cosign.

We should extend and integrate this existing infrastructure rather than introduce another independent SBOM-generation system.

In particular, release publishing should ensure that all distributed container images, including operator images, have an associated SBOM and verifiable provenance.

### 9.2 SBOM publishing

For every container image belonging to a release, CI should:

1. Generate or retrieve the CycloneDX SBOM associated with its immutable image digest.
2. Verify that the SBOM corresponds to the image included in the release manifest.
3. Preserve the existing signed attestation and provenance.
4. Make the SBOM accessible to users through the GitHub Release or a permanent artifact reference.

The initial requirement should be **one SBOM per released container image**, rather than a single repository-level SBOM.

An optional aggregate SBOM or SBOM index may be generated to make it easier to inspect all components of the CobaltCore distribution.

Chart dependency inventories can be added separately where applicable.

### 9.3 Provenance and integrity

CI should retain the existing signing and attestation mechanisms and extend verification to the release assembly process.

The release workflow should verify:

- Container image digests.
- Helm chart artifact identities and integrity.
- SBOM availability and association with the correct artifact.
- The source commit used to produce each artifact.
- The checksums of downloadable release assets.

The release manifest should provide enough information for users to locate and independently verify the published artifacts.

Stable promotion must preserve existing signatures, SBOM associations, and build provenance.

Security metadata should be retained for the supported lifetime of a release, rather than depending on short-lived GitHub Actions artifacts.

## 10. Automated Release Notes

Release notes should be generated automatically by CI/CD and published with every release.

The goal is to avoid manually reconstructing changes from Git commits and pull requests while still providing information useful to operators and users.

### 10.1 Release note generation

We propose using GitHub's automatically generated release notes, configured through `.github/release.yml`.

Release notes should be derived primarily from merged pull requests, using labels to categorize changes.

The following categories are proposed:

- **Features:** Newly introduced functionality.
- **Bug Fixes:** Corrections to existing behavior.
- **Breaking Changes:** Changes requiring user intervention or migration.
- **Dependencies:** Significant dependency and component updates.
- **Documentation:** User-facing documentation changes.
- **Other Changes:** Relevant changes not covered by another category.

PR labels should be the primary mechanism for categorization. Squashed commit messages should retain enough context to trace a change back to its original PR.

### 10.2 Release note content

Automatically generated changelogs should be supplemented with a short, maintainer-reviewed summary.

Each release should contain:

#### 10.2.1 Highlights

The most significant functionality or improvements included in the release.

#### 10.2.2 Changes

Automatically generated categorized changelog with links to merged pull requests and the full commit comparison.

#### 10.2.3 Compatibility

Supported OpenStack and Kubernetes versions, with links to the release compatibility matrix.

#### 10.2.4 Breaking Changes and Upgrade Instructions

Changes that require migration, configuration updates, or special attention during upgrades.

#### 10.2.5 Known Issues

Known limitations or outstanding issues relevant to deployments.

#### 10.2.6 Artifacts and Verification

Links to installation manifests, Helm charts, the release manifest, SBOMs, and verification instructions.

### 10.3 RC and stable release notes

RC release notes should describe the candidate's scope and known limitations.

For successive RCs, the release notes should also identify changes made since the previous candidate.

The cumulative changelog should compare against the previous stable release, or an explicitly chosen baseline for the first release.

CI must use an explicit comparison baseline so that unrelated changes from `main` or other release branches do not appear in release notes.

The stable release should reuse the approved cumulative release notes from the promoted RC, with the RC identifier and stable promotion information added.

Maintainers should review the generated notes before stable publication, especially breaking changes, compatibility claims, and upgrade guidance.

## 11. GitHub Release Publishing and CI/CD Automation

The existing GitHub Actions release infrastructure should be extended to automate the release lifecycle.

### 11.1 Release candidate workflow

When maintainers initiate a candidate release from `release/0.1`, CI should:

1. Verify that the selected commit belongs to the expected release branch.
2. Verify that required checks and release gates have passed.
3. Create the immutable RC Git tag.
4. Build and publish the required container images and Helm charts, or collect already built artifacts by verified digest.
5. Generate the installation manifests.
6. Generate the release manifest and compatibility matrix.
7. Collect or generate SBOMs and verify artifact provenance.
8. Generate release notes and calculate asset checksums.
9. Create a draft GitHub Release and attach the completed artifact set.
10. Publish the RC as a GitHub pre-release.

The release must not be marked ready until all required artifacts are available and their integrity has been verified.

### 11.2 Stable promotion workflow

Stable promotion should be a separate, explicitly approved operation.

The workflow receives the RC tag to be promoted and its target stable version.

For example:

`v0.1.0-rc.3` → `v0.1.0`

It should then:

1. Verify that the RC exists and that its validation has been approved.
2. Verify that the RC source commit and artifact digests match the release manifest.
3. Verify that all required artifacts and security metadata are present.
4. Create the stable Git tag at the exact same source commit.
5. Create a stable GitHub Release that references the same deployable artifacts.
6. Publish the approved release notes and promotion metadata.

No component rebuild, manifest regeneration, or Helm chart repackaging should take place during stable promotion.

Distribution-level aliases may be introduced where technically supported, but they must resolve to the exact previously published content.

The stable GitHub Release should be marked as the latest release, while RCs remain identified as pre-releases.

### 11.3 Existing workflow changes

The initial implementation should extend the current workflows rather than replace them.

The main areas of work are:

| Area | Required change |
|---|---|
| `.github/workflows/ci.yaml` | Support PRs and release validation on `release/*` |
| `.github/workflows/build-images.yaml` | Support release branches while retaining digest-based publication and supply chain checks |
| GitHub Release job | Publish the full release artifact set, release notes, and compatibility information |
| Release notes configuration | Introduce `.github/release.yml` and agreed PR labels |
| Release promotion | Introduce an approved RC-to-stable promotion workflow |
| Supply chain | Ensure SBOM and provenance coverage for every released image |

The existing `github-release` job already supports GitHub Releases on `v*` tags and generates release notes, but currently attaches operator Helm chart archives only.

It should be adapted so that RC and stable publication have different behavior, with stable promotion explicitly skipping artifact builds.

The existing tag-triggered publishing behavior must also be changed so that stable tags cannot overwrite chart or image versions used by existing releases.

### 11.4 Release immutability

Published Git tags and release artifacts should be immutable.

The publishing workflow should reject attempts to replace an existing release version with different content.

Where supported, GitHub's immutable release protections should be enabled. Release assets must be assembled before publication when immutability is enforced.

## 12. Alternatives Considered

### 12.1 Releasing directly from `main`

This would be simpler to operate, but would make stabilization dependent on the ongoing development stream.

Release branches allow development to continue while a specific release is being tested.

### 12.2 Introducing additional channels

We could introduce channels such as `alpha`, `beta`, or `nightly`.

For now, RC and Stable should provide sufficient separation without introducing unnecessary complexity. Development builds from `main` can continue to exist without becoming a formal release channel.

### 12.3 Rebuilding stable artifacts

Rebuilding from the same commit might produce equivalent functionality, but does not guarantee identical artifacts.

Promoting the validated RC provides stronger reproducibility and a clearer audit trail.

### 12.4 Manually maintained release notes

Maintainers could write every release note manually.

However, automated generation from PR metadata reduces repetitive work and makes the process more consistent. Manual review should remain focused on user-facing summaries and migration guidance.

### 12.5 A single distribution-level SBOM

A combined SBOM could simplify distribution-level inspection, but may obscure which dependencies belong to which image.

Individual, digest-associated SBOMs are the preferred baseline, with an aggregate index as an optional convenience.

## 13. Open Questions

The following details should be agreed upon before implementation:

1. **Validation requirements:** Which CI suites and real-environment tests are mandatory before an RC can be promoted?
2. **Release ownership:** Who is responsible for approving and executing stable promotion?
3. **Component versioning:** How should independently versioned components relate to the coordinated CobaltCore distribution?
4. **Compatibility policy:** Which Kubernetes and OpenStack compatibility checks are required before declaring a release supported?
5. **Security gates:** Should any vulnerability severity or missing attestation block a release, and what exception process should apply?
6. **Release maintenance:** How long should release branches and stable release series receive fixes?

## 14. Success Criteria

This RFC is considered implemented when maintainers can:

- Cut a release branch without interrupting development on `main`.
- Publish successive immutable RCs.
- Backport selected fixes through reviewed pull requests.
- Validate RC artifacts in representative environments.
- Generate release notes automatically from merged pull requests.
- Publish a coordinated artifact set, including installation manifests and compatibility information.
- Identify and retrieve SBOMs and provenance for every released container image.
- Trace every released component to a specific source revision and artifact digest.
- Promote an RC to stable without rebuilding deployable artifacts.
- Publish a complete GitHub Release containing the artifacts and documentation defined in #1617.

The intended outcome is a release process that is straightforward for maintainers to execute and predictable, transparent, and verifiable for users to consume.
